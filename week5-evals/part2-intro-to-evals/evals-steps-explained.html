AI Engineering · Introduction to evals

Choose the model from evidence. Then keep it honest.

Eight short steps in four lessons. You pick a model by measuring instead of guessing, learn to grade free-text answers, fix the prompt before paying for a bigger model, and keep it all working after you ship.

The job the model does

It reads a short incident report and pulls out three fields:

{"service": "checkout", "severity": "sev2", "root_cause": "A config push set the connection pool size to 5."}

service and severity have exactly one right value. root_cause is a sentence that can be written many ways, and it should be null when the report doesn't say what caused the problem.

Case
One real report, plus the answer a person says is right. We have 24.
Grader
Whatever decides if the model's answer is right: a bit of code, another AI model (a “judge”), or a person.
Run
All 24 cases through one model with one prompt. You get scores and a bill.
Floor
The lowest score you'll accept. Ours is 90%.
Lesson 1

Which model?

1

Pick a model with numbers

step1_pick_a_model.py

First you decide how good is good enough. The review team can fix about 1 bad report in 10, so 90% must be right. Then you run three models (small, medium, large) on the same 24 cases with the same prompt.

You compare them by cost per completed task: the whole bill divided by the answers that were fully right. A cheap model that gets a lot wrong isn't really cheap.

modelrightcost per 1,000 right answers
small79%$0.030
medium100%$0.093
large96%$0.487
Like: hiring. You don't hire the most expensive person. You hire the cheapest one who can actually do the job.

Small is cheapest but below the floor, so medium wins, for now.

Lesson 2

A minimum viable eval

2

A judge for the sentence

step2_judge.py

Checking service and severity is easy: plain code compares them exactly. But step 1 checked the root cause by counting shared words, and that's too crude. The same cause can be said in different words.

So another AI model becomes the judge. It reads the report, the answer and a written rubric (rules for “correct” and “incorrect”). It does not see our expected answer, so a right answer in other words isn't punished. It's also allowed to say “unknown” instead of guessing.

No new model calls: the judge regrades the answers step 1 saved. Two cases change:

caseword checkjudge
large · “Pool limit dropped to five after a bad configuration deploy.”wrongcorrect
small · “The cache layer (suspected, not confirmed).”wrongunknown
Like: a multiple-choice exam is marked by a machine, but an essay question needs a teacher with a marking guide.

Use code where there's one right answer, and a judge with a rubric where there isn't.

3

Check the judge

step3_calibrate.py

Before trusting the judge, compare it with a person. Someone graded 24 answers by hand. The judge agreed on 23. The one disagreement: the report said the cause was “suspected, not confirmed”. The person said that's not a real cause. The rubric didn't say either way, so the judge said “unknown”.

The fix is one new line in the rubric: a suspected or unconfirmed cause doesn't count. Now the judge agrees on all 24.

Like: a new teaching assistant. You check their first batch of marking. Where you disagree, you clarify the marking guide.

Every disagreement is a rule missing from the rubric. Write it down.

Lesson 3

Fix the prompt first

4

Read the failures

step4_read_failures.py

A low score doesn't tell you if the model is weak or the prompt is unclear. So you read the small model's 5 failures and group them.

4 of the 5 are the same mistake: the report states no cause, and the model invented one anyway. It turned a reassurance (“we don't expect the certificate renewal to cause problems”), a fix (“restarted the pods”), a suspicion and a symptom into causes. The 5th mixed up the severity after it was downgraded.

Like: a doctor looks at the symptoms before prescribing. Buying a bigger model without reading the failures is guessing.

The old prompt said “or null” but never said when null applies.

5

Fix the prompt, decide again

step5_fix_the_prompt.py

Prompt v2 adds three things: say exactly when the root cause is null; copy the sentence from the report that states the cause before answering (no sentence, no cause); and use the final severity if it changed. Then all 24 cases run again on all three models.

model · promptrightcost per 1,000 right answers
small · v179%$0.030
small · v2100%$0.048
medium · v2100%$0.192

The longer prompt makes each call a bit pricier, but the small model now clears the floor, and it's the cheapest. No answer that was right before became wrong.

Fix the prompt before buying a bigger model. Here, the small model won.

Lesson 4

Evals in production

6

A quick test on every change

step6_smoke_eval.py

After you ship, people edit the prompt. A “cleanup” can delete the very line that fixed a problem. So every pull request runs a small, fast eval: 8 cases covering every kind of report. If fewer than 7 of 8 pass, the check fails and the change can't be merged.

changesmoke evalmerge
current prompt (v2)8 of 8allowed
a PR that “simplifies” it back to v15 of 8blocked
Like: a smoke detector. It doesn't check everything, but it catches the fire before it spreads.

The lines that looked like clutter were the fix. Let the eval guard them.

7

The full test, at half price

step7_batch.py

The full suite (every case on every model, 72 requests) doesn't need an answer in a minute. You send it as one batch. The provider finishes it within 24 hours at half the price.

The answers come back in any order, so each request carries its own label (like r06__small) and you match by that label, never by position.

Like: sending laundry out overnight instead of express. Same result, cheaper, just later.

Small and fast for every change; full and cheap in batches.

8

Notice when the world changes

step8_drift.py

Even if nobody touches the prompt, real inputs change over time. This is called drift. So every night you take a small random sample of real reports (5%, about 20), and the judge grades them. No expected answers needed.

You only alert on a real drop: much lower than the last 7 nights (more than 2 standard deviations below). On night 14 a new tool starts writing “Priority: P2” instead of “Severity: sev2”. The model copies “P2”, which isn't a valid severity.

nightsscore
last 7 nights90–100% (alert below 86.7%)
night 1455% · alert
Like: a regular health check-up. You're not sick today, but you'd want to know early when something starts slipping.

Every wrong answer from production becomes a new test case, and the loop starts again.

About the numbers. These come from Replay mode, which needs no API key: the model and judge answers are scripted, but the grading, costs and decisions are computed for real. In Live mode, with real models, your numbers will differ, and they'll vary from run to run. Run each setup twice before you trust it.
