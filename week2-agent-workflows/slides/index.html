How we judge a pattern

Four questions, every time

  1. 01How many calls? Calls are money and latency. Count them before you draw the boxes.
  2. 02What does each call see? Every call gets a context window. Smaller and more focused usually means better.
  3. 03Can I test one step alone? If you can’t isolate a step, you can’t tell which step broke.
  4. 04How does it fail? Loudly, silently, or by looping forever. Pick the failure you can live with.

An agent is a loop

Call the model with tools. If it asks for a tool, run it in your code and hand the result back. Stop when it answers without asking. Everything else today is built on top of these lines.

01 · Agent fundamentals

Reasoning LLMs vs agents

Reasoning LLM

  • Spends extra tokens thinking before it answers
  • Still one request, one response
  • Can’t look anything up or change anything
  • Better at planning, maths and multi-step logic

Agent

  • A model in a loop with tools
  • Acts, sees the result, decides again
  • Touches files, APIs, databases, the web
  • Any model can drive it, but reasoning models drive it better

A reasoning model is a better brain. An agent is a brain with hands and a loop. They compose.

01 · Agent fundamentals

Tools

  1. 01A tool is four things a name, a description, a JSON schema for its arguments, and your function.
  2. 02The model only proposes it emits a tool call; your code decides whether and how to run it.
  3. 03Read vs write reading is cheap to allow. Anything that changes the world goes behind a permission check.
  4. 04The description is a prompt most “the model is dumb” bugs are a vague tool description or a confusing schema.

01 · Agent fundamentals

MCP & Skills

MCP · access

  • A protocol: an MCP server exposes tools, resources and prompts
  • Any MCP client can connect: an IDE, a chat app, your own agent
  • It standardises the plug, not what the tool does
  • Write the integration once, use it from every client

Skills · know-how

  • A folder with a SKILL.md, plus optional scripts and reference files
  • Only the name and description sit in context until needed
  • Teaches the agent how to do a job, step by step
  • Can ship code, so install them like dependencies: from sources you trust

MCP gives the agent new abilities. A skill tells it how to use the ones it has. You often want both.

Anatomy of a skill

The frontmatter is all the agent carries around. When a task matches the description, it reads the body, and only then the files the body points at. That is how a skill protects the context window.

01 · Agent fundamentals

RAG

Retrieval-augmented generation: index your documents ahead of time, then at question time fetch the few chunks that look relevant and put them in the prompt. New knowledge without retraining.

Use when

The answer lives in documents the model has never seen: policies, catalogues, your codebase.

Watch for

When RAG is wrong it is usually retrieval, not generation. Measure whether the right chunk came back.

01 · Agent fundamentals

Context

  1. 01The window is the agent’s whole world on every call: system prompt, tools, history, retrieved text, tool results.
  2. 02More is not better long, noisy context makes models miss what matters, and every token is paid for again on every turn.
  3. 03Fetch just in time retrieve or read when needed instead of loading everything up front.
  4. 04Compact and offload summarise old turns, write notes to files, give a sub-task its own clean window.

01 · Agent fundamentals

Agent memory

Short-term

  • The model is stateless; the message list is the memory
  • Goal, conversation, tool results, scratch notes
  • Lives in the context window, so it has to be curated

Long-term

  • Semantic: facts and documents, often searched with RAG
  • Episodic: what happened before, past runs and their lessons
  • Procedural: how to behave, from system prompts, rules files and skills

The long-term split comes from the CoALA paper (Sumers et al., 2023). It gives you a vocabulary for where a fact should live.

01 · Agent fundamentals

Planning & reflection

Planning · before acting

  • Break the goal into steps before taking the first one
  • Keep the plan in context, like a todo list, so long tasks stay on track
  • A plan is a hypothesis. Revise it when a step surprises you

Reflection · before finishing

  • Check the work against criteria before calling it done
  • Signals the model can’t fake (tests, linters, validators) beat self-opinion
  • Every round costs a call. Cap the rounds

Planning decides what to do. Reflection decides whether it worked, and often triggers a new plan.

02 · Non-agent workflows

Prompt chaining

Split the task into fixed steps. Each call does one step and its output becomes the next call’s input. Between steps, plain code can check the output and stop or retry.

Use when

The task splits cleanly into the same steps every time: outline, draft, translate, format.

Watch for

Latency adds up step by step, and an early mistake poisons everything after it. Check at the gates.

Pouria Jahandideh · AI Agent Workflows18 / 45
02 · Non-agent workflows

Routing

One cheap call classifies the input, then code sends it down the path built for that class: a specialised prompt, a cheaper model, or no LLM at all.

Use when

Inputs fall into distinct kinds that deserve different handling, or easy ones can go to a small model.

Watch for

A wrong route fails quietly. Log every decision and give the router an “unsure” path.

Pouria Jahandideh · AI Agent Workflows19 / 45
02 · Non-agent workflows

Parallelization

Run several calls at once and combine the results. Sectioning splits the work into independent parts. Voting runs the same task several times and takes the consensus.

Use when

The parts don’t depend on each other, or you want more confidence: guardrails, reviews, classifications.

Watch for

You pay for every branch. The aggregator is a design problem of its own: what if the branches disagree?

02 · Non-agent workflows

A workflow is just functions

No framework needed. Chaining is calling one function after another, routing is a switch statement, parallelization is Promise.all. You can unit-test every line.

03 · Single-agent systems

ReActYao et al., 2022

Reason, then act, then observe, then reason again. The model writes down a thought, makes a tool call, reads the result, and decides the next move until it can answer.

Use when

Open-ended tasks where the next step depends on what you just found: research, debugging, support.

Watch for

Without a step limit and a clear definition of done, it wanders. Cap steps, log every thought.

03 · Single-agent systems

Plan & execute

A planner writes the whole plan up front, then an executor works through it step by step. When a step fails, go back to the planner instead of improvising.

Use when

Long tasks with a predictable shape, where a strong planner and a cheaper executor save money.

Watch for

Plans go stale when reality surprises you. If the steps never change, you may just want a workflow.

Pouria Jahandideh · AI Agent Workflows26 / 45
03 · Single-agent systems

Reflection & self-refiningMadaan et al., 2023 · Shinn et al., 2023

Generate, critique, revise. In self-refine the model critiques its own draft. In Reflexion a real failure, like a failing test, produces a written lesson that the next attempt carries.

Use when

Quality is checkable: tests pass, a schema validates, a rubric is clear.

Watch for

A model grading itself with no outside signal tends to approve its own work. Cap the rounds.

Pouria Jahandideh · AI Agent Workflows27 / 45
03 · Single-agent systems

CodeActWang et al., 2024

Instead of one JSON tool call per step, the agent writes a small program as its action. Loops, variables and composition happen in one move, in a language the model has seen a lot of.

Use when

Many small operations over data: filtering, joining, calculating, batch edits.

Watch for

You are running code a model wrote. That belongs in a sandbox with no secrets and no open network.

04 · Multi-agent systems

Sequential agents

A pipeline like prompt chaining, except every stage is a full agent with its own prompt, tools and maybe model. Each stage can plan, retry and check its own work before handing off.

Use when

Clear stages that need different tools or expertise: research, then write, then review.

Watch for

Errors compound down the line and latency stacks. Define the handoff format and validate it.

Pouria Jahandideh · AI Agent Workflows32 / 45
04 · Multi-agent systems

Multi-agent parallelization

Fan the request out to several agents at once, each with its own clean context, then merge. Sectioning splits the work; voting has several agents attempt the same thing.

Use when

Broad questions with independent threads: research across sources, reviewing many files.

Watch for

Fast in wall-clock time, expensive in tokens. Merging conflicting findings is the hard part.

Pouria Jahandideh · AI Agent Workflows33 / 45
04 · Multi-agent systems

Supervisor

One agent keeps the big picture. It breaks the task down as it goes, briefs subagents, reads what they return and decides what next. Subagents never need to know about each other.

Use when

You can’t list the subtasks in advance, and each one benefits from a narrow, clean context.

Watch for

The supervisor is the bottleneck and the biggest bill. A vague brief to a subagent wastes a whole run.

Pouria Jahandideh · AI Agent Workflows34 / 45
04 · Multi-agent systems

Dispatcher

The multi-agent version of routing. A triage step reads the request and hands it to exactly one specialist agent. Only one path runs: it is a fork, not a decomposition.

Use when

Requests fall into distinct domains with different tools: billing, technical support, sales.

Watch for

A wrong handoff is hard to recover from. Let specialists hand back, and escalate when unsure.

Pouria Jahandideh · AI Agent Workflows35 / 45
04 · Multi-agent systems

Evaluator-optimizer

One agent does the work, a second agent judges it and sends back a critique, and the loop repeats until the evaluator passes it or a limit is hit.

Use when

There is a clear bar to clear (tests, a rubric, a spec) and quality matters more than cost.

Watch for

Context grows every round. Always set a max-iteration cap and a timeout.

Pouria Jahandideh · AI Agent Workflows36 / 45
04 · Multi-agent systems

Peer-to-peer

No coordinator. Agents message each other directly and pass work around until a stop condition fires. Every agent has to know about every other agent.

Use when

Rarely. Debates, simulations, problems with no natural hierarchy.

Watch for

The connections grow faster than the agent count. Hardest to debug: a last resort, not a default.

Proving any of it works

Pouria Jahandideh · AI Agent Workflows39 / 45
05 · Evaluation

What to measure

  1. 01Outcome did the world end up in the right state? Right answer, right file changed, right ticket closed.
  2. 02Trajectory did it get there sensibly? Check for forbidden actions, but don’t demand one exact path.
  3. 03Cost and latency next to success, on the same report. A 2% gain at 3× the cost is a different decision.
  4. 04Benchmarks aren’t your evals they test someone else’s task, usually once, usually only accuracy.
Pouria Jahandideh · AI Agent Workflows40 / 45
05 · Evaluation

pass@k vs pass^k

pass@k · at least one

  • Chance that at least one of k attempts succeeds
  • Goes up as k grows
  • Right when you can verify and keep the best one, like code with tests
  • 70% per run → pass@3 ≈ 97%

pass^k · every one

  • Chance that all k attempts succeed
  • Goes down as k grows
  • Right for user-facing agents, where every run is someone’s experience
  • 70% per run → pass^3 ≈ 34%

Same agent, same 70%. One number says ship it, the other says not yet. pass^k comes from τ-bench (Yao et al., 2024).

Pouria Jahandideh · AI Agent Workflows41 / 45
05 · Evaluation

Build your own evals

  1. 01Start from real failures 20 to 50 tasks taken from what actually went wrong beat a thousand synthetic ones.
  2. 02Binary pass/fail a clear check you can automate beats a fuzzy 1–10 score.
  3. 03Test the negatives cases where the agent should not call the tool, refund, or delete.
  4. 04Clean, repeatable environments as close to production as you can, reset on every run.
  5. 05Run on every change prompts, tools and models are all code. Evals are their tests.

So what do I use?

Climb only when the rung below fails

  1. 01One good callA single prompt with the right context. Most features stop here.
  2. 02A workflowYou know the steps. One or two of them need an LLM.
  3. 03One agentThe path is unknown, but the set of tools is known.
  4. 04Many agentsTruly independent sub-problems, or more context than one window can hold.

“Fails” means fails your evals, not that it feels too simple.
